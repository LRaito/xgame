# release-note：按 tag 生成 GitHub Release 发布说明

输入一个版本 tag，输出一份可直接粘进 GitHub Release 的中文 Markdown。

- 只生成文件，**不提交、不推送、不创建 GitHub Release**。
- 文件写在仓库外（默认 `/tmp/release-note-<tag>.md`），
  生成后在回复里给出路径，由用户自己复制。
- 本技能只读 Git 历史，不跑测试、不改代码。

## 用法

```
/release-note v1.2.0
```

- **版本 tag 必填。** 带不带前导 `v` 都行，统一按仓库里实际存在的标签名输出。
- 没给 tag 时先问用户，并列出最近的标签：
  `git tag --sort=-creatordate | head -10`
- tag 不存在就停下，列出可用标签，不要猜范围。
- 用户另外指定了起始版本时，以用户为准；否则自动取上一个 tag。

## 收集范围

在仓库根目录执行：

```bash
TAG=v1.2.0
git rev-parse --verify "$TAG^{commit}"          # 标签必须存在
PREV=$(git describe --tags --abbrev=0 "$TAG^")  # 上一个标签
git rev-list --count "$PREV..$TAG"              # 提交总数，写进导语
git log "$PREV..$TAG" --format='%h|%s'          # 逐条归类
git log -1 --format=%cs "$TAG"                  # 发布日期
```

- 首个版本没有上一个标签时，范围用 `$TAG` 全量，导语不提「上一个版本」。
- 发布日期默认取 tag 指向提交的日期（`%cs`）；
  用户明确给了发版日期就用用户的。
- 提交标题只用来定位改动，**不要照搬进正文**。
  需要判断一条改动是否用户可见、属于哪个功能时，再看：
  `git show --stat <hash>`，必要时 `git show <hash>`。
- 涉及数据库结构、部署方式、外部素材的改动，要再读对应的 `docs/` 文件确认操作步骤。

## 归类

先按提交类型分流，再按功能合并：

| 提交类型 | 去向 |
|---|---|
| `feat` | 「新增」，用户可见的行为变化 |
| `fix` | 「修复」 |
| `refactor` / `chore` / `docs` | 默认不单列；改变了用户可见行为或升级步骤时并入相应章节 |

- **一个功能只写一条。**
  同一功能的多条提交（新增、调整、再修复）合并成最终形态，不按提交逐条罗列。
- **只写净结果。**
  加了又删掉的功能不写；中间过程不写。
- **纯内部改动省略。**
  脚本日志格式、依赖 digest、文档措辞、测试、目录整理，不构成用户可感知的改动。
  其中影响升级操作的（如索引不再自动构建、数据库需要手动升级）写进「升级与注意」。
- **抓取、裁图一类开发脚本**默认不写进「新增」，
  除非用户能直接用到（例如随平台发布的功能）。

分类小节按主题起名，参考：

| 主题 | 常见关键词 |
|---|---|
| 游戏发现 | 检索、榜单、名录、catalog、rankings |
| 游戏与封面 | 封面、卡带、美化、机壳 |
| 播放器 | 模拟器、启动页、滤镜、布局 |
| 游戏中心 | 侧栏、统计栏、筛选、卡片 |
| 管理与交付 | 管理页、Docker、Windows 包、数据库升级、make |
| 账号与页面 | 登录、会话、按键管理、机型简史 |

本版本没有内容的主题不要建小节。

## 格式

按下面的骨架输出，标题层级、加粗、空行都保持一致：

```markdown
# v1.2.0

**发布日期：2026-11-14**

本次发布汇总 v1.1.0 之后的 80 项改动：接入新机种、重做游戏榜单与机型简史，并补上数据库结构升级工具与流式上传。

## ✨ 新增

### 机种支持

- 新增 Commodore、世嘉 CD、Amiga、PSP、DOS 与街机机种。
- 新增多文件本体与文件名播放。

### 游戏与封面

- 新增 SFC 封面美化与机壳。
- 新增游戏中心类型侧栏与统计栏。

## 🐛 修复

- 修复登录后偶现被踢下线。
- 修复搜索框点清空时重复请求接口。

## ⚠️ 升级与注意

- **Docker**：`git pull` 后执行 `make upgrade`，再执行 `make all`。
- **数据库**：结构版本不匹配时服务会拒绝启动，先停服务再升级。
- **新机种**：BIOS 与 core 资产不随仓库提供，缺失时播放页会提示。
```

### 文字要求

- 全文中文，标点用全角；`Docker`、`NDS`、`H5`、`BIOS`、`make` 这类术语保留原文。
- 一条一件事，一句话说完，不写从句套从句。
- 每条以动词开头：`新增` / `支持` / `改为` / `修复` / `移除`。
- 写用户看到的效果，不写实现：
  - 不写文件名、函数名、路由、表名、commit hash。
  - 不写「重构了 XX 服务」，改写成用户能感知的变化；感知不到就不写。
- 有具体数量、按键、机种、格式时写出来，不用「若干」「部分」。
- 「新增」按主题分 `###` 小节，每节内按重要性排序，不按提交时间。
- 「修复」不分小节，按影响面从大到小排。
- 「升级与注意」按对象分行，用加粗前缀开头：
  `**Docker**：` / `**Windows**：` / `**数据库**：` / `**新机种**：`
  没有对应内容的不写。
- 导语一句话说清本版本的主线，不重复下面的条目。
- 不写「详见代码」「细节略」「其他改动」这类空话。

## 自检

写完后逐项确认：

- [ ] 标题版本号与 tag 一致，日期与 tag 指向的提交一致。
- [ ] 导语里的提交数与 `git rev-list --count` 一致。
- [ ] 每个用户可见的功能都在正文里，没有按提交流水账重复。
- [ ] 没有出现代码路径、函数名、commit hash。
- [ ] 新增小节没有空节，每节至少一条。
- [ ] 升级步骤能照着做，涉及数据库与外部素材的都写到了。
- [ ] 文件在仓库外，`git status` 没有新文件。

## 交付

- 用 Write 工具写到 `/tmp/release-note-<tag>.md`。
- 回复里给出路径、覆盖的版本区间（`<上一个 tag> → <tag>`）和提交数。
- 用户在对话里要正文时，直接贴 Markdown 原文，不再复述结构。
